# 설계 문서

## 1. 전체 구조

- **EOS**: 로그인 신원 확인만 담당 (Connect 인터페이스의 PUID, 토큰). EOS Sessions/Lobbies의 매칭 기능은 쓰지 않는다.
  - EOS 매칭은 속성 검색 기반이라 MMR/큐 기반 자동매칭이 없다 -> 직접 구현하는 것이 이 프로젝트의 핵심
- **TCP 매칭 서버 (이 저장소)**: 로그인 세션 확립, 플레이어 정보, 방, 자동매칭, 데디 서버 관리/할당
- **언리얼 데디케이티드 서버**: 실제 게임(리플리케이션, 게임 로직). 게임 로직은 클라 팀원이 담당
- 리슨 서버가 아니라 데디 서버를 쓴다. 이유: 매칭 후 접속할 고정 주소가 필요, 서버 권한/검증, 방장 이탈 시 게임 종료 문제

## 2. 역할 분담

- 서버 파트(사용자): TCP 서버, 데디 서버와 TCP 서버 연동(상태 보고, 입장 티켓 검증, 결과 보고)
- 클라 파트(팀원): 데디 서버 접속 이후의 게임 전체, 로비/로그인/방 UI. 서버 권한 구조(서버가 판정, 클라는 요청/표시)로 만들 것
- 서버 쪽은 클라가 쓸 수 있게 `Login()`, `CreateRoom()`, `RequestMatch()` 같은 함수와 결과 이벤트로 감싼 언리얼용 클라이언트 래퍼를 제공한다
- 팀에 공유하는 것은 패킷 정의와 클라용 래퍼뿐. 서버 내부 코드는 이 저장소에서 사용자가 관리한다

## 3. 로그인 흐름

1. 클라이언트가 EOS로 로그인해 토큰(JWT)을 받는다
2. TCP 서버에 연결해 `LoginRequest(토큰)` 전송
3. 서버가 토큰 검증 (EOS 공개키로 JWT 서명 검증 또는 EOS Web API)
4. 통과하면 PUID로 DB에서 플레이어 로드/신규 생성, 연결(Session 객체)에 붙인다
5. `LoginResponse(성공, 플레이어 정보)` 이후부터 방/매칭 요청을 받는다
- 개발 초기에는 닉네임만 보내는 가짜 로그인으로 진행하고 나중에 EOS 토큰 검증으로 교체한다
- 개발 중 EOS 로그인은 Connect의 Device ID(익명 로그인)로 시작하면 팀원이 Epic 계정 없이 테스트 가능
- 중복 로그인 정책, 재접속, 로그아웃 시 저장, 연결 끊긴 유저의 큐/방 정리가 필요하다

## 4. 데디 서버 연동

데디 서버가 TCP 서버에 클라이언트처럼 접속해 연결을 유지한다.

1. 데디 서버 시작 -> `D2S_Register` (serverId, ip, port, build)
2. 2초마다 `D2S_Status` (Idle/InGame, 인원). 하트비트 겸용, 6초 이상 없으면 죽은 서버로 제거
3. 매칭 성사 -> TCP 서버가 빈 서버를 골라 `S2D_Allocate` (matchId, 플레이어별 1회용 티켓)를 데디 서버에 **먼저** 전달
4. 동시에 클라에게 `서버 주소 + 본인 티켓` 전달 -> 클라가 `ClientTravel("IP:Port?Ticket=xxx")`
5. 데디 서버 GameMode::PreLogin에서 받아둔 티켓과 대조, 없으면 입장 거부
6. 게임 종료 -> `D2S_Result` -> TCP 서버가 MMR/전적 저장, 서버를 Idle로 복귀
- 티켓을 미리 내려주는 이유: PreLogin에서 TCP 서버 왕복(비동기 대기) 없이 즉시 판단
- 연결이 끊기면 데디 서버가 3초마다 재접속하고 매번 Register를 다시 보낸다 (어느 쪽이 재시작해도 복구)
- 할당 직후 하트비트 전 중복 할당을 막기 위해 Reserved 상태를 둔다
- 테스트 모드: 데디 서버를 `-NoAuth`로 실행하면 TCP 연결/티켓 검사를 생략 (클라 팀원이 서버 없이 작업)
- 티켓에는 만료 시간(약 30초)을 둔다

## 5. 패킷 (shared/PacketDefs.h)

프레임: `[uint16 BodyLen][uint16 PacketId][Body]`. 본문은 우선 JSON, 이후 Protobuf로 교체 가능.

- D2S_Register=100, D2S_Status=101, D2S_Result=102
- S2D_RegisterAck=200, S2D_Allocate=201
- 클라 <-> 서버(로그인, 방, 매칭) 패킷 ID는 이 저장소에서 정의한다 (미정)

## 6. 구현 순서

1. 비동기 TCP 서버 뼈대 + 다중 접속 (에코 서버)
2. 패킷 프레이밍 (분할/병합 수신 처리, 비정상 길이 차단)
3. 더미 클라이언트로 100개 동시 접속 테스트
4. 로그인 + 플레이어 정보 (가짜 로그인 -> 저장소는 SQLite)
5. 방 생성/입장/퇴장/방장 위임/목록
6. 데디 서버 등록/상태 보고
7. 자동매칭: 큐, MMR 매칭(대기 시간에 따라 허용 범위 확대), 방 자동 생성, 데디 서버 할당
8. 입장 티켓 검증, 결과 보고
9. EOS 토큰 검증으로 로그인 교체
- 가장 막힐 지점: 동시성 버그, 연결 끊김 처리(큐/방/게임 중 어느 시점이든 상태가 안 꼬여야 함), 소스 빌드 엔진 세팅

## 7. 환경 결정

- 개발 초기에는 런처 엔진 + 에디터 Play As Client(에디터가 데디 서버를 띄움)로 테스트. 구조는 데디와 동일
- 데디 서버 실행 파일 패키징과 클라우드 배포가 필요해지면 소스 빌드 엔진으로 전환 (팀 전체가 같은 엔진 버전이어야 함)
- 네트워크 라이브러리는 Asio (Windows에서는 내부적으로 IOCP). 국내 면접 대비로 IOCP 에코 서버를 별도 학습용으로 만들어 볼 수 있음
- git은 로컬 `git init`으로 시작, 진행되면 private 저장소로 백업. worktree는 병렬 작업이 생길 때 도입
- 후순위(생략 가능): 서버 자동 증설, Redis
