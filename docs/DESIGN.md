# 설계 문서

## 1. 전체 구조

- **외부 인증 서비스(EOS 등)는 쓰지 않는다** (2026-11-19 결정). 계정, 로그인, 방, 데디 할당을 모두 직접 만든다.
  - 이유: 계정 DB, 비밀번호 해시, 로그인 세션, 서버 권한 보상 저장까지 서버 파트에서 직접 설명할 수 있어야 한다
- **TCP 매칭 서버 (이 저장소)**: 회원가입/로그인(MySQL 계정 DB), 로그인 세션 확립, 플레이어 정보, 방, 데디 서버 관리/할당
- **MySQL**: 계정, 플레이어 정보, (이후) 보상/전적. TCP 서버만 접속한다. 클라와 데디 서버는 DB에 직접 붙지 않는다
- **언리얼 데디케이티드 서버**: 실제 게임(리플리케이션, 게임 로직). 게임 로직은 클라 팀원이 담당
- 리슨 서버가 아니라 데디 서버를 쓴다. 이유: 매칭 후 접속할 고정 주소가 필요, 서버 권한/검증, 방장 이탈 시 게임 종료 문제

## 2. 역할 분담

- 서버 파트(사용자): TCP 서버, 데디 서버와 TCP 서버 연동(상태 보고, 입장 티켓 검증, 결과 보고)
- 클라 파트(팀원): 데디 서버 접속 이후의 게임 전체, 로비/로그인/방 UI. 서버 권한 구조(서버가 판정, 클라는 요청/표시)로 만들 것
- 서버 쪽은 클라가 쓸 수 있게 `Login()`, `CreateRoom()`, `RequestMatch()` 같은 함수와 결과 이벤트로 감싼 언리얼용 클라이언트 래퍼를 제공한다
- 팀에 공유하는 것은 패킷 정의와 클라용 래퍼뿐. 서버 내부 코드는 이 저장소에서 사용자가 관리한다

## 3. 로그인 흐름

ID + 비밀번호, MySQL 계정 DB (2026-11-19 결정, M1에 포함).

1. 클라가 TCP 서버에 연결한다. 이 시점의 Session은 "로그인 전" 상태라 회원가입/로그인 패킷만 받는다
2. 회원가입: `C2S_Register(id, password, nickname)` -> 서버가 salt를 만들어 비밀번호를 해시하고 `accounts`에 INSERT -> `S2C_RegisterResult`
3. 로그인: `C2S_Login(id, password)` -> 서버가 `accounts`에서 해시를 읽어 대조 -> `S2C_LoginResult(성공, 플레이어 정보)`
4. 성공하면 계정을 Session에 붙이고(SessionManager), 이후부터 방 요청을 받는다
5. 일정 시간(예: 10초) 안에 로그인하지 않으면 서버가 끊는다

- **DB 쿼리는 로직 스레드에서 직접 하지 않는다.** 쿼리는 블로킹이라 로직 스레드가 멈추면 모든 유저가 멈춘다.
  로직 스레드 -> DB 스레드(전용 io_context 또는 큐)로 요청을 넘기고, 결과를 다시 로직 스레드로 post한다
- 비밀번호는 평문 저장 금지. salt + 느린 해시(argon2/bcrypt 계열, 예: libsodium `crypto_pwhash`)로 저장한다
- 로그인 실패 응답은 "ID 없음"과 "비밀번호 틀림"을 구분하지 않는다 (계정 존재 여부 노출 방지)
- SQL은 prepared statement로만 실행한다 (SQL 인젝션 방지)
- 비밀번호가 TCP 평문으로 오간다. M1은 LAN/로컬 시연이라 허용하고, 이후 TLS 적용을 검토한다
- DB 접속 정보는 커밋하지 않는 로컬 설정 파일(`config/local*.json` 등)에서 읽는다
- 중복 로그인 정책(기존 연결을 끊는다), 재접속, 로그아웃 시 저장, 연결 끊긴 유저의 방 정리가 필요하다

테이블 초안:
```sql
CREATE TABLE accounts (
  account_id    BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  login_id      VARCHAR(32)  NOT NULL UNIQUE,
  password_hash VARCHAR(128) NOT NULL,   -- salt와 파라미터를 포함한 해시 문자열
  nickname      VARCHAR(32)  NOT NULL UNIQUE,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_login_at DATETIME     NULL
);
```

## 4. 데디 서버 연동

데디 서버가 TCP 서버에 클라이언트처럼 접속해 연결을 유지한다.

1. 데디 서버 시작 -> `D2S_Register` (serverId, ip, port, build)
2. 2초마다 `D2S_Status` (Idle/InGame, 인원). 하트비트 겸용, 6초 이상 없으면 죽은 서버로 제거
3. 매칭 성사 -> TCP 서버가 빈 서버를 골라 `S2D_Allocate` (matchId, 플레이어별 1회용 티켓)를 데디 서버에 **먼저** 전달
4. 동시에 클라에게 `서버 주소 + 본인 티켓` 전달 -> 클라가 `ClientTravel("IP:Port?Ticket=xxx")`
5. 데디 서버 GameMode::PreLogin에서 받아둔 티켓과 대조, 없으면 입장 거부
6. 게임 종료 -> `D2S_Result` -> TCP 서버가 MMR/전적 저장, 서버를 Idle로 복귀
- 티켓을 미리 내려주는 이유: PreLogin에서 TCP 서버 왕복(비동기 대기) 없이 즉시 판단
- 연결이 끊기면 데디 서버가 3초마다 재접속하고 매번 Register를 다시 보낸다 (어느 쪽이 재시작해도 복구)
- 할당 직후 하트비트 전 중복 할당을 막기 위해 Reserved 상태를 둔다
- 테스트 모드: 데디 서버를 `-NoAuth`로 실행하면 TCP 연결/티켓 검사를 생략 (클라 팀원이 서버 없이 작업)
- 티켓에는 만료 시간(약 30초)을 둔다

## 5. 패킷 (shared/PacketDefs.h)

프레임: `[uint16 BodyLen][uint16 PacketId][Body]`. 본문은 우선 JSON, 이후 Protobuf로 교체 가능.

- D2S_Register=100, D2S_Status=101, D2S_Result=102
- S2D_RegisterAck=200, S2D_Allocate=201
- 클라 <-> 서버(로그인, 방, 매칭) 패킷 ID는 이 저장소에서 정의한다 (미정)

## 6. 구현 순서

2026-11-19 M1(12/7, 로그인 -> 방 -> 데디 진입) 기준으로 다시 정리했다.

1. 비동기 TCP 서버 뼈대 + 다중 접속 (에코 서버) - 완료
2. 패킷 프레이밍, 송신 큐, 로직 스레드, 네트워크/로직 분리 - 완료
3. 로그인: SessionManager, 로그인 전 차단/타임아웃, MySQL 계정 DB, DB 스레드, 회원가입/로그인
4. 언리얼 로비 클라 래퍼 (접속, 프레이밍, 수신 스레드 -> 게임 스레드, Register/Login)
5. 방 생성/목록/입장/퇴장/시작, 인원 변경 브로드캐스트
6. 데디 서버 등록/상태 보고, 시작 시 할당 -> ClientTravel
7. (M1 이후) 입장 티켓 검증, 결과 보고와 보상 저장(DB), 방장 위임, 재접속
8. (M1 이후) 더미 클라이언트 100개 동시 접속 부하 테스트
9. (M1 이후, 선택) 빠른 참가/MMR 자동매칭
- 가장 막힐 지점: 동시성 버그, 연결 끊김 처리(큐/방/게임 중 어느 시점이든 상태가 안 꼬여야 함), 소스 빌드 엔진 세팅

## 7. 환경 결정

- 개발 초기에는 런처 엔진 + 에디터 Play As Client(에디터가 데디 서버를 띄움)로 테스트. 구조는 데디와 동일
- 데디 서버 실행 파일 패키징과 클라우드 배포가 필요해지면 소스 빌드 엔진으로 전환 (팀 전체가 같은 엔진 버전이어야 함)
- 네트워크 라이브러리는 Asio (Windows에서는 내부적으로 IOCP). 국내 면접 대비로 IOCP 에코 서버를 별도 학습용으로 만들어 볼 수 있음
- git은 로컬 `git init`으로 시작, 진행되면 private 저장소로 백업. worktree는 병렬 작업이 생길 때 도입
- DB는 MySQL. 로컬에 MySQL 서버를 설치해 개발한다. C++ 클라이언트 라이브러리는 vcpkg로 받는다 (후보: `libmysql` C API, `mysql-connector-cpp`. 3단계 시작 때 결정)
- 후순위(생략 가능): 서버 자동 증설, Redis

## 8. 포트폴리오에 남길 것

- 계정/로그인을 직접 만든 이유와 구조 (DB 스레드 분리, 비밀번호 해시, 중복 로그인 처리)
- 방/데디 할당을 서버 권한으로 처리한 이유 (클라가 아닌 서버가 판정)
- 아키텍처 다이어그램과 흐름
- 더미 클라이언트 부하 테스트 수치 (동시 접속, 매칭 소요 시간)
